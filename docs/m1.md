# M1：跑一次真实验，拿到你自己的 `human_offset_ms`

> M1 只回答一个问题：**机器说"就是现在"，人真的会在那一刻动手吗？误差有多小、多稳？**
> 如果答案是"稳定"，后面所有设计（协议、MCP、硬件降级）才立得住；
> 如果误差是纯噪声，诚实的结论是"去买继电器，别做这个"。

前置：`docs/implementation-notes.md`（实现笔记，含实测数字与已知边界）。

## 二、跑实验

**必须在一个真终端窗口里**（Windows Terminal / cmd / PowerShell 皆可），不要通过管道或后台任务。

```bash
cd path/to/chrono-handoff
export PYTHONPATH=src

# 30 次，交替测 "有 beep" 和 "纯视觉" 两种条件
python -m chrono_handoff.cli probe --trials 30 --conditions both,visual
```

> ⚠️ **协议已于首次真实验后修正（重要）**：GO 拍之后默认再播 6 拍（`--tail-beats 6`）。
>
> 原因：原来把节拍**截在 GO 那一拍**，等于让人"等 GO 出现再按"—— 这测的是**反应时**，不是拍点同步。真实验第一轮就暴露了它：`both`(+114ms) 与 `visual`(+105ms) 几乎一样，说明偏移来自两条通道共用的响应路径，而非 cue 通道本身。
>
> **GO 之后节奏必须继续**，人才可能进入 anticipation 模式。传 `--tail-beats 0` 可复现旧行为（用于对照）。

**每次的样子**：

```
--- trial 3/30  [both] ---
    PRESS SPACE exactly on the GO beat
    GO beat lands t+6.0s
    press Enter when ready...        ← 你按 Enter，倒计时才开始
  [################........]   7 beats
  ...
  >>> GO <<<
    -> -42.0 ms  (applied +0.0)  status=satisfied
```

**怎么按**：

- 按 Enter 后你会听到 **`嘀 嘀 嘀 …`** 的拍子，每 500 ms 一拍。
- **最后一拍音色不同（更高更响）** —— 那一拍就是 GO，你要**踩在它上面**按空格。
- 不要等听到再按 —— 那时你已经晚了。要**跟着节拍律动**，第 N 拍和手指同时到。
- 前 2 次是热身（`--warmup 2`），不计入统计。

**按错了**：没按到也没关系，那次记成 `no signal` 并计入 `missed`，不影响其它轮。

## 三、看结果

```
==================================================================
  M1 RESULT -- human offset against a beat grid
==================================================================
  counted 28  with-signal 26  missed 2
  (offsets are signed: NEGATIVE = human fired early, POSITIVE = late)

  condition    n    median     MAD      sd      min      max  %early
  both        13     -42.0ms   26.4ms   31.2ms  -96.0ms    8.0ms   92.3%
  visual      13     -18.0ms   58.7ms   71.5ms -145.0ms  112.0ms   61.5%
  # ^ 这是修正协议后**期望**看到的形态：负值（提前）、%early 高、两者有区分度

  overall     n=26  median=-31.0ms  MAD=39.6ms  spread=227.0ms
  machine scheduling error: median-of-medians=0.02ms worst=1.85ms
  VERDICT: premise_supported
==================================================================
```

### 怎么读

| 字段 | 含义 |
|------|------|
| **median** | 你的系统性偏差。**负数 = 你倾向提前**（这是正常且预期的） |
| **MAD** | 稳健抖动。**这是最重要的一列** —— 它决定"时间锚定"有没有意义 |
| **%early** | 提前的比例。拍点同步下通常 > 50% |
| **machine scheduling error** | 机器自己的落点误差。**必须 ~0.1 ms 量级**；如果不是，bug 在 conductor，不在你 |
| **residual** | 应用学到的偏移**之后**的剩余偏差。**~0 表示校准真的抵消了你的偏差** |

### 判定标准（预注册，避免事后解释）

| spread (MAD) | 结论 | 含义 |
|--------------|------|------|
| **≤ 60 ms** | `premise_supported` | 偏移小且稳，时间锚定有意义，常数部分可被校准消除 |
| ≤ 120 ms | `marginal` | 可用但勉强；值得调拍距 / 换提示方式 |
| > 120 ms | `premise_weak` | 比预期噪声大得多；考虑硬件执行器 |

## 四、关键实验：校准是否真的有效

**这是本项目全部价值所在**，必须单独测一次：

```bash
python -m chrono_handoff.cli probe --trials 24 --conditions both \
    --calibrate-every 3 --warmup 0 --store .tmp/cal.json
```

含义：每 3 轮之后，把学到的偏移应用到后续轮次。

**要看到的现象**：

```
    -> +65.0 ms  (applied  +0.0)     ← 前 3 轮：未校准，暴露你的固有偏差
    ...
    -> +65.0 ms  (applied +65.0)     ← 之后：cue 被提前 65ms
```

然后看报告的 `residual`：

```
  residual after applying the learned offset: median=+1.2ms MAD=0.0ms
```

**`residual` 从几十毫秒降到个位数 = 校准成功 = 人机在同一时刻相遇。**

再对比一下你的校准库：

```bash
python -m chrono_handoff.cli calibrate
```

## 四点五、不想用声音 / 不能听声音

**声音不是必须的。** 这个机制依赖的是**周期性**，不是"声音"这个感官 —— 只要节拍可预测，用哪个通道都能进入 anticipation 模式。

默认用 beep 的真实理由有两条，分量不同：

| 理由 | 强度 |
|------|------|
| 听觉时间分辨率高于视觉（毫秒级 vs 几十毫秒） | 中等 |
| **听觉不占用眼睛** | ★ 强得多 |

第二条才是决定性的，而且直指目标场景：**PMON 那 3 秒里，操作员的眼睛正盯着串口输出。** 视觉 cue 会与被观测对象抢同一个通道；声音是平行通道。

**纯视觉怎么跑**：

```bash
python -m chrono_handoff.cli probe --trials 30 --conditions visual --audio null

# 视觉样式可选（默认 marker 就是为"当节拍器用"设计的）
python -m chrono_handoff.cli probe --trials 20 --conditions visual --audio null --visual-style marker
python -m chrono_handoff.cli probe --trials 20 --conditions visual --audio null --visual-style bar
```

| `--visual-style` | 形态 | 说明 |
|------------------|------|------|
| `marker`（默认） | 每拍跳一格的方块 `......o......` | **整行都在变**，每拍有强 onset |
| `flash` | marker + 拍前清空一帧 | 制造 off→on 跳变，视觉更易定位 |
| `bar` | 经典进度条 + 剩余拍数 | 每拍只变一个字符，**不推荐当节拍器** |

> ⚠️ **一个测量效度问题**：早先版本的视觉通道每拍只让进度条变 3~4 个字符（28格/8拍），位置固定、对比度低。用它测出的"视觉很差"，会混进"我们的视觉提示很烂"这个混杂因素。所以默认样式已改为 `marker`。**如果你需要视觉方案，务必说明用了哪个 style** —— 否则数据不可比。

**完全不能看也不能听**：触觉。手机震动在时间同步上与听觉**相当**，明显优于视觉。`HttpSource` 已经就绪，配一个手机页面即可（M3 做）。

## 五、几个值得单独跑的对照

```bash
# 纯听觉（闭眼也能做，最接近"跟随节拍"的本质）
python -m chrono_handoff.cli probe --trials 20 --conditions audio

# 纯视觉（对照：beep 的增益有多大？）
python -m chrono_handoff.cli probe --trials 20 --conditions visual

# 完全无提示（对照下界，应该很差）
python -m chrono_handoff.cli probe --trials 12 --conditions silent

# 拍距的影响（理论预期：~500ms 最易进入 anticipation；>2s 会退化成 reaction）
python -m chrono_handoff.cli probe --trials 20 --conditions both --ioi 250
python -m chrono_handoff.cli probe --trials 20 --conditions both --ioi 1000
```

把结果写进报告：

```bash
python -m chrono_handoff.cli probe --trials 30 --conditions both,visual --out .tmp/m1-a.json
```

## 六、没有真终端时：先验证机器（用合成人类）

不需要人也能验证整条链路是否正确：

```bash
# 验证机器：注入已知偏差，看能否原样恢复
python -m chrono_handoff.cli selftest

# 端到端 dry-run（合成人类固定 +80ms，验证自适应校准）
python -m chrono_handoff.cli probe --trials 12 --source sim --sim-offsets 80 \
    --conditions both --calibrate-every 3 --warmup 0 --auto \
    --audio null --no-visual --store .tmp/cal.json
```

预期：`residual = +0.0 ms`。这是**机器正确性的证明**，不能替代真人数据。

## 六点五、离线分析（拿到数据后先做这一步）

```bash
python -m chrono_handoff.analyze --glob 'logs/<session_id>_*.jsonl'
```

它会报告：

| 项 | 用途 |
|----|------|
| MACHINE 落点误差 | 确认 cue 准确（median 应 ~0.0ms）。**若不是，bug 在 conductor，不在人** |
| HUMAN 按条件分组偏移 | 主结果 |
| **WHICH BEAT THE PRESS FOLLOWED** | ★ 关键诊断：如果多数人跟错拍（如跟着 GO 后第 1 拍），那"偏移大"是 **cue 设计问题**，不是人的精度问题 |
| HONEST OFFSET | 相对于"他实际跟随的那一拍"的误差，剔除了跟错拍的影响 |
| DRIFT | 前后半场对比，看学习/疲劳 |

**先看 `WHICH BEAT`，再看 offset。** 如果那栏显示人跟错了拍，后面所有 offset 数值都不可信。
