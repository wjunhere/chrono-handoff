# 问题定义与量化

## 1. 问题的本质

LLM agent 是一个**纯软件实体**：

- 它能读写文件、发网络请求、写串口 —— 只要这些操作有软件接口
- 它**不能**按一个物理按钮、插拔一根线、给设备上电
- 当操作必须由人类完成时，agent 只能"请求 → 等待 → 得知结果"

看起来只是"等一会儿"的问题，实际上是**架构性的不匹配**。

## 2. 量化：延迟 vs 窗口

### 2.1 三个时间尺度

| 主体 / 环节 | 典型耗时 | 说明 |
|------------|---------|------|
| **LLM 一次推理 turn** | **5 ~ 30 秒** | 含网络往返、思考、工具调度、输出生成 |
| 人类执行物理动作 | 0.1 ~ 1 秒 | 按下按钮本身；但"意识到该按"更慢 |
| 物理世界给的窗口 | **毫秒 ~ 秒级** | 取决于场景，可能极窄 |

### 2.2 典型场景的窗口宽度

| 场景 | 窗口宽度 | 人类能否跟上 |
|------|---------|-------------|
| BIOS/PMON 引导菜单 | **1 ~ 5 秒** | 边缘可行（需看着屏幕） |
| ARM U-Boot 中断 | 1 ~ 3 秒 | 边缘可行 |
| Android fastboot / 组合键进 recovery | 数百 ms ~ 2 秒 | 困难 |
| 网络协议握手窗口（DHCP 抢注、ARP 竞争） | 数十 ~ 数百 ms | ❌ 做不到 |
| 电机/舵机的控制周期 | 10 ~ 50 ms | ❌ 完全做不到 |

### 2.3 致命的不等式

```
LLM turn (5~30s)  ≫  物理窗口 (0.05~5s)
```

**LLM 的反应时间比物理窗口长 1~2 个数量级。**

所以"人做完 → 通知 agent → agent 反应"这条链路，在任何窗口 < 30 秒的场景里**注定失败**。

## 3. 为什么"优化 prompt / 让 agent 反应快点"救不了

即使把 LLM 推理压到极限（假设 2 秒），仍然会有：

1. **网络往返**：本地 vs 云端的 API 延迟
2. **思考时间**：模型生成 token 的时间
3. **工具调度**：harness 处理 tool call 的开销
4. **人类告知 agent 的时间**：人按下按钮后，agent 怎么知道？串口回读本身有延迟
5. **多个 turn 的累积**：如果 agent 需要两步（先看状态，再决定），延迟翻倍以上

**这不是工程调优问题，而是"控制回路的时间常数选错了"。**

## 4. 反例：agent 做到过什么

需要说明的是，agent 并非在所有物理交互上都无能为力：

| 能做到 | 原因 |
|--------|------|
| 通过串口发送命令序列 | 软件接口，可在单个 tool call 内连续执行 |
| 写一个脚本，让脚本做定时操作 | **脚本是独立进程，不受 LLM turn 延迟影响** ★ 关键 |
| 在窗口内高频轮询尝试（抢占） | 只要 tool call 已经启动，内部循环就不受延迟影响 |
| 控制有网络/软件接口的设备 | 有软件接口 |

**共同点：一旦动作进入"独立进程执行"的范畴，LLM 的延迟就不再是瓶颈。**

这直接指向解决方案：**把时间敏感的部分从 LLM turn 里搬出去。**

## 5. 问题的正确表述

> ❌ 错误表述："agent 反应太慢，需要更快。"
>
> ✅ 正确表述：**"与物理世界的时间耦合方式选错了 —— 应该用时间触发（预先约定时刻），而不是事件触发（等待通知后反应）。"**

关键推论：

1. 时间敏感的动作必须**提前提交**，不能事后决策
2. 执行时间敏感动作的必须是**独立于 LLM turn 的进程**
3. 人类若参与，必须给**明确的时间锚点**（倒计时 + 声音），而不是"你做完告诉我"
4. 必须有**反馈闭环**，因为"我发了命令"≠"事情发生了"

## 6. 现有做法的不足

### 6.1 阻塞式 HITL（Human-in-the-Loop）

现有工具（`human-intervention-mcp`、`call-a-human-mcp`、`human-mcp` 等）的模式：

```
agent 调用 tool → tool 弹出 UI/发消息 → 阻塞等人 → 人操作完 → tool 返回 → agent 继续
```

**解决了什么**：agent 不知道人类何时完成 → 现在知道了
**没解决什么**：agent 仍然在人类动作**之后**才开始决策 —— 时间敏感的动作依然错过窗口

### 6.2 盲目 `sleep`

```python
send("reboot")
time.sleep(30)      # 赌 30 秒后 PMON 菜单还在
send("c")
```

**问题**：
- 猜的时间必然不准（重启耗时受系统负载影响）
- 窗口只有 3 秒，而 `sleep` 的误差可能是 ±5 秒
- 一旦猜错，没有任何补救

**实测教训**（详见案例研究）：`sleep(15)` 的结果是抢到了 AUTO 启动都已经加载完 27MB initrd 的时刻。

### 6.3 纯轮询抢占（改进但仍不完整）

```python
send("reboot")
for _ in range(250):
    serial.write(b'c')      # 每 0.3 秒发一次
    time.sleep(0.3)
```

**解决了**：窗口命中率 → 近乎 100%
**没解决**：需要人类介入的那些动作（按 Reset）依然没有时间对齐手段

**这正是本项目要补的那块。**

## 7. 问题清单（待解决）

| # | 问题 | 本项目对策 |
|---|------|-----------|
| P1 | LLM 延迟 ≫ 物理窗口 | 预先提交 timeline，独立进程执行 |
| P2 | 人类不知道何时该动 | 倒计时 + 声音锚点 |
| P3 | 人类动作有时间抖动 | 动作给"窗口"而非"单点"，窗口内重复尝试 |
| P4 | 无法知道人类是否真的动了、动得对不对 | 传感器回读闭环验证 |
| P5 | 人类可能漏做/早做 | re-arm 重装填 + 幂等设计 |
| P6 | 毫秒级窗口人类根本做不到 | 降级到硬件执行器（GPIO 继电器等） |
| P7 | 阻塞等待在长任务里不可靠（客户端超时、状态丢失） | 计划持久化 + 可恢复（durable checkpoint） |
