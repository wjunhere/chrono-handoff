# M1 实现笔记：设计里看不出来的那些事

> 记录于 M1 完成时（`cli.py` / `conductor.py` / `clock.py` / `cue.py`）。
> 本文只写**动手之后才知道的东西** —— 纯设计阶段不可能预见，但会决定项目成败。
> 所有数字都是本机（Windows 11 · CPython 3.13）实测。

---

## 一、实测数字：这些直接改变了设计

### 1.1 时钟层

| 操作 | 实测 | 结论 |
|------|------|------|
| `time.perf_counter()` 分辨率 | 0.1 µs，相邻间隔中位数 0.2 µs | 够用，单调时钟是唯一选择 |
| `time.sleep(1ms)` 超出量 | **0.62 ms 中位 / 0.78 ms 最大** | ❌ 拍点最后一段不能用 sleep |
| sleep → busy-wait spin | **0.001 ms 中位 / 0.003 ms 最大** | ✅ 最后 2 ms 必须 spin |
| 20 拍 20ms 网格落点 | 中位 0.015 ms / 最大 0.058 ms | 亚毫秒，符合预期 |
| 40 拍 50ms 网格总漂移 | +0.009 ms / 2 秒 | 绝对值网格不累积漂移 |

**设计后果**：`wait_until()` 先粗睡（0.5ms 粒度）再 spin 最后 2 ms。这不是优化，是正确性前提。

### 1.2 音频通道

| 方式 | 调用开销 | 阻塞 |
|------|---------|------|
| `winsound.PlaySound(file, SND_FILENAME\|SND_ASYNC)` | **0.25 ms 中位 / 最大 3 ms** | 非阻塞 ✅ |
| `winsound.Beep(880, 30ms)` | 实际阻塞 **34.5 ms** | ❌ 禁用 |
| `winsound.MessageBeep(0)` | 0.53 ms | 非阻塞但音色不可控 |
| `winsound.PlaySound(mem, SND_MEMORY\|SND_ASYNC)` | — | ❌ **Windows 不支持**（`RuntimeError: Cannot play asynchronously from memory`） |

**设计后果**：
- 拍点回调**只能**用 `PlaySound(file, ASYNC)`；必须预渲染 WAV 到磁盘。
- `Beep` 若放进拍点，会吃掉 3 秒窗口的 1%+ 且抖动不可控 —— **这正是"倒计时只是装饰品"的实现级成因**。
- 首次调用有一次性的设备初始化开销（实测 2.4~8 ms），`doctor` 必须先 warm 再测稳态。

### 1.2b 精度的真实下限（含尾部）★

300 拍 @ 20ms，**空回调**（不放我们任何代码）：

| median | p90 | p99 | max | >1ms 占比 |
|--------|-----|-----|-----|----------|
| 0.019 ms | 0.055 ms | 1.808 ms | 3.136 ms | **2.7%** |

**关键**：尾部尖峰在**空回调**下同样存在 → 它来自解释器/OS 层（GIL 交接、gen-2 GC、Windows 调度器），**不是 conductor 造成的**。

给日志加一次队列入队后：p90 从 0.055 → 0.075 ms。**我们自己的工作不是瓶颈。**

**这条教训要记住**：一开始我看到回调 `executed_s` 高达 7.9 ms，以为是同步写日志的锅。**错了** —— `executed_s` 量的是跨回调的墙钟时间，**包含线程被抢占的时间**。控制变量重测后，空回调一样有 3 ms 尾部。

> **量因，别量相关时序。**

**工程结论**：报告要同时给 median 和尾部百分位。典型 0.019ms + p99 2ms，与"均匀亚毫秒"是两种不同的仪器，只报 median 会掩盖它。两者都比人类的 ~50ms 低两个数量级。

### 1.3 GIL —— 纯 Python 方案的精度天花板 ★

2 个 CPU 满载的兄弟线程 + 50ms 网格：

| `sys.setswitchinterval` | 落点中位 | 最差 |
|------------------------|---------|------|
| 5.0 ms（Python 默认） | **10.455 ms** | **29.497 ms** |
| 1.0 ms | 9.014 ms | 43.138 ms |
| **0.5 ms** | **0.260 ms** | 4.905 ms |
| 0.1 ms | 0.253 ms | 5.171 ms |

**这是本项目最重要的实现发现**：默认 GIL 切换间隔会把亚毫秒调度变成 10~30 ms 调度 —— 而 10 ms 抖动对 3 秒窗口已经相当可观。

**设计后果**：`Scheduler.start()` 自动调 `sys.setswitchinterval(0.0005)`。
**但必须诚实地承认这是缓解而非根治**：只要有 CPU 密集的 Python 线程，抖动上限就是 5 ms 量级（实测 3.6~5.2 ms）。

**因此写进架构约束**：
> **所有耗时计算必须放在独立进程，不能放在 conductor 进程的其他线程里。**
> 串口读、HTTP、日志落盘可以（IO 等待会释放 GIL）；解析、编码、图像、numpy 一律外移。

真需要亚毫秒且高负载时，选项是：① 把 conductor 缩到只做调度 + 调 C 层音频 API；② 换实时内核 / 独立进程独占核。**M1 不需要，但必须知道边界在哪。**

## 二、三个"只有动手才会发现"的 bug

这三个都不是设计错误，而是**实现语义错误**，且**在单次运行里完全看不出来**。

### 2.1 远期任务会饿死后来者（最严重）

**现象**：M1 dry-run 报机器调度 `worst=3801 ms`。

**根因**：调度线程取堆顶任务后直接 `wait_until(deadline)`。若堆顶是 3 秒后的任务，而此刻提交了一个 0.25 秒后的新任务，**必须等满 3 秒才会被看见**。

```
heap top = A @ +3.0s   ← 线程开始朝它睡
   ↓ (提交 B @ +0.25s)
sleep 到 +3.0s 才发现 B 已经过期 2.75s  →  B 迟到数秒
```

**为什么致命**：真实人类会在提交后立刻开始看倒计时。如果拍点被推迟 3 秒，**倒计时根本不会正常发生**，而单次手动测试很可能凑巧不触发（取决于提交时刻的堆状态）。

**修复**：`_wait_for_top()` 分片等待 —— 超过 spin 阈值就每 2 ms 重新检查堆顶是否已变，只有最后 2 ms 才一路 spin 到底。新增任务的可见延迟从"堆顶时间跨度"降到 ~2 ms。

**回归测试**：`clock: late-arriving work is not starved`（在 +3s 任务在顶时提交 +0.25s 任务，要求落点误差 < 20 ms）。

### 2.2 计数网格限流是坏的

**现象**：旧版把 count 编码成 `skipped = -count`（负数当"无限"哨兵），`_reschedule` 里把哨兵和"已跳过拍数"混用。

**后果**：一个 run 的拍网格**不会停**。它继续按**上一个 run 的调度**触发，于是 run N 的动作落进 run N+1 的测量窗口 —— 单次测不出来，聚合统计被污染。

**修复**：显式 `remaining: int | None`（None = 无限），每次 reschedule 精确扣减 `1 + behind`。

**回归测试**：`clock: counted grid stops at count`。

### 2.3 网格首拍必然迟到

**现象**：`worst` 恒有 ~10~13 ms 的尖峰，且**每次都出现在第一拍**。

**根因**：`origin` 在 `_arm_run()` 开头就打了时间戳，之后还要写若干事件（`cue_origin`、`beats_planned`…）。而网格第 0 拍被安排**正好等于 `origin`** —— 等调度器真正武装时，那个时刻**已经过去了**，于是首拍必然迟到。

**修复**：从"第一个**仍在未来**的格点"开始，跳过够不到的领跑拍。**格点本身不动**（`zero_at` 分毫未变，人类锚点不受影响），只跳过无法兑现的领跑拍——人是数到 GO 那一拍，不是数第一拍。

**顺带**：这也说明审计口径要收紧。`run_end` 里统计的 `sched_offset_ms` 现在**只统计 `{run_id}:beats`**，因为 deadline / window 任务在收尾时是被主动拆除的，它们的触发"迟到"是设计使然，混进来会伪装成 cue 抖动。

### 2.4 停止时遗留任务污染审计

**现象**：`probe` 报 `worst=8.3 ms`。

**根因**：`Conductor.stop()` 先停调度线程，堆里还剩的远期任务在关闭过程中被触发，落点极晚，被记进 firing 审计，而 M1 的判定要读这个数。

**修复**：关闭前先 `cancel_all()`，再停线程。

## 三、平台坑（Windows / Git Bash）

| 坑 | 表现 | 处理 |
|----|------|------|
| `SND_MEMORY\|SND_ASYNC` | `RuntimeError` | 只用 `SND_FILENAME` |
| `SO_REUSEADDR` 语义反转 | **两个 conductor 同时监听同一端口**，连接随机分配 | Windows 用 `SO_EXCLUSIVEADDRUSE`；并加"先探测是否已有实例"的前置检查 |
| 单实例探测的时序 | 第二个实例先打印 "listening" 再失败 | `bind()` 必须**早于**任何 banner 输出 |
| `msvcrt` 需要真控制台 | 管道/重定向下 `kbhit()` 永远不触发 | `doctor` 报 `console: NO`；源不可用时**降级并记账**，不崩溃 |
| MSYS 路径 | Windows Python 不认 `/tmp/x` | 测试用项目内目录 |
| 跨层转义 | bash → Python heredoc 里 `\n` 被吃掉，产生假语法错误 | 用 `edit` 工具改文件，不用 heredoc 生成代码 |

## 三点五、协议设计错误：GO 拍不能是最后一拍 ★

**这是 M1 最重要的一条发现，而且它是我的设计错误，不是仪器问题。**

### 现象

真实验数据（n=18，干净子集）：

| 条件 | median | sd |
|------|--------|-----|
| `both`（声音+视觉） | +114.0 ms | 100.7 ms |
| `visual`（纯视觉） | +104.5 ms | 59.8 ms |

**两个条件几乎一样。** 这个事实本身就是线索：如果偏移来自音频输出延迟，纯视觉应该显著更小。它没有 → 偏移来自**两条通道共用的部分**。

而且 +105 ms / sd 58 ms 是典型的 **reaction（反应）**特征，不是 **anticipation（预期）**特征。

### 根因

原协议把节拍网格**截在 GO 那一拍**：

```
嘀 嘀 嘀 嘀 嘀 嘀 GO          ← 然后就没了
                     ↑
              最后一拍后面没有节奏了
```

**后果**：人无法"进入节奏"，只能"等 GO 出现再按" —— 这在结构上**必然是反应时**。

而 NMA（negative mean asynchrony，人会略早）只在**节奏持续**时才涌现。也就是说：**我把一个同步任务，实现成了一个反应时任务。**

### 修复

新增 `CuePlan.tail_beats`（默认 6）：GO 之后继续播 N 拍。

```
嘀 嘀 嘀 嘀 嘀 嘀 GO 嘀 嘀 嘀 嘀 嘀 嘀
                   ↑
            节奏继续，人可以锁定脉动
```

三处配套改动：

1. **`cancel_cue_on_signal`**（默认 `True`）。生产环境里"人一动就停提示"是对的；但**当 cue 本身是被研究对象时必须是 `False`** —— 否则人一按就静音，他永远学不到"GO 后面还有拍"，下一轮又退回反应。这是"停止提示"与"停止刺激"的区别。
2. **`cue_audit` 事件独立**：网格跑完才发，而不是 `run_end` 时。否则尾拍还没触发，审计会少记。
3. **`probe` 必须等 cue 网格跑完再开始下一轮**，否则上一轮的尾拍会串进下一轮的倒计时，人听到的是"永不停歇的节拍"。

### 教训

> **测量一个能力之前，先确认协议真的在测那个能力。**

`+105 ms 且 0% 提前` 这个结果，如果不去看"两个条件为什么一样"，就会被解读成"人类在拍点同步上就是晚 105ms"—— 一个完全错误的、会写进论文的结论。**是条件间的对比（而不是绝对数值）暴露了设计错误。**

## 四、M1 实测结果与解读

### 4.0 第一次真实验（协议修正前，n=18）★ 保留

| 条件 | n | median | sd | %early |
|------|---|--------|-----|--------|
| `both` | 9 | +114.0 ms | 100.7 | 0% |
| `visual` | 9 | +104.5 ms | 59.8 | 12% |
| 合计 | 18 | +107.1 ms | 89.1 | — |

**机器侧（同时段 204 拍）**：median **0.0 ms**，max **0.3 ms**。

**解读**：
- ✅ **机器侧完美**：204 拍中位 0.0ms、最大 0.3ms。cue 的精确投放已经被验证。
- ⚠️ **人工侧是反应时特征**，因为协议把 GO 做成最后一拍（见 §三点五）。**这批数据不能用于判断"人能否做拍点同步"**，只能用于确认"人能否对一个一次性信号作出反应"。
- ⚠️ **样本被污染过**：`m1_000`~`m1_011` 共 12 个 trial 与早期 dry-run 撞名（见 §五）。已隔离到 `logs/_contaminated/`，上表是排除后的干净子集。

**数据卫生的教训（同样要记）**：

1. **run id 必须含会话 token**。原用确定性的 `m1_{index:03d}_{condition}`，导致两次运行的 journal 写到同一个文件并 **append 叠加**。已改为 `{session_id}_{index:03d}_{condition}`。
2. **多进程 append 同一文件在 Windows 上不是原子的**。实际观测到一行被撕裂成 `'56},"wall":1789900017.0'` —— 从数字中间开始。分析器现在对撕裂行容错，但那行数据永久丢失。
3. **不要在项目日志目录里跑 dry-run**。分析脚本新增 `--last N`，并且必须显式指定 glob。

### 4.1 合成人类（验证整条链路）

```
注入 offset: [-40, 0, 60, 120] ms
恢复 offset: [-40.0, 0.0, 60.0, 120.0] ms
最大误差 0.00 ms
```

两条独立的单时钟路径（`SimSource` 独立记录时刻 vs `conductor` 从 cue_zero 推算）取得一致结果，说明**cue → 观测 → 统计**这条链路在数值上无偏。

### 4.2 自适应校准收敛（项目的核心主张）

合成人类固定 +80 ms 偏差，`--calibrate-every 3`：

| trial | 应用偏移 | 测得 offset |
|-------|---------|------------|
| 1–3 | 0 | +65.0 |
| 4–12 | **+65.0** | +65.0 |

**结果**：`residual = 0.00 ms`。

即：**机器学到"这个人晚 65 ms"，然后把 cue 提前 65 ms，人机在同一时刻相遇。** 项目的核心主张在合成人类上严格成立。

（+80 注入 → +65 测得，差的 15 ms 正是 `key_latency_s` 修正值，符合定义。）

### 4.3 校准器的稳健性

对 20 次 `N(45, 25)ms` 采样：估计 50.4 ms（误差 5.4 ms，MAD 13.3 ms）。
注入一次 **5000 ms 异常值**：估计仅移动 **+0.0 ms**。

median + MAD + 单次步进夹紧（30ms）+ 总偏移夹紧（±300ms）共同保证了"一次走神不会毁掉整个会话的校准"。

### 4.4 一个我判断错的例子（保留，作为教训）

见 §1.2b。简版：

1. 看到回调 `executed_s` 最高 7.88 ms → 判断"同步写日志阻塞了计时线程"
2. 改成异步日志线程 + 先打时间戳再动作
3. 重测：尾部尖峰**依旧存在**
4. 控制变量（空回调）→ 尾部来自解释器/OS，**与日志无关**

异步日志**保留**了，但理由换成"**按构造就不该把磁盘 I/O 放在拥有时钟的线程上**"（磁盘延迟、杀毒、网络盘这些故障模式在干净基准里不出现，在真机器上会出现），**而不是**"修复了一个实测 bug"。

代价：p90 增加 ~0.02 ms。

### 4.5 负载下的诚实数字

2 个 CPU 满载兄弟线程：中位 **0.459 ms** / 最差 **3.649 ms**。

这是纯 Python conductor 的真实能力上限，**不是可以忽略的数字**，但远优于 10~30 ms 的默认 GIL 行为，且远小于人类 ±50 ms 的抖动 —— 所以对 M1 结论不构成威胁。

## 五、与文档的偏离（需回填 `design.md`）

| 原设计 | 实现后 | 理由 |
|--------|--------|------|
| `t0 = timeline 提交时刻` | `t0 = cue_origin`（`go()` 那一刻） | 人可能在提交后 40 秒才看到提示；锚提交时刻会让倒计时凭空消失 |
| 单一 `sync_action` | `submit` / `go`(paused) / `observe` / `wait` / `verify` | 提交与等待必须分离，否则又变回阻塞 |
| `human_latency_ms` | `human_offset_ms`（**有符号**，负=早） | 拍点同步下人会**提前**（NMA），字段名不能暗示恒正 |
| `expect_signal.pattern` 归 source 管 | 归 conductor 的 `match()` | 同一串口要同时服务 `expect`（字节到达）与 `verify`（进入引导符）；匹配是 per-run 策略，source 只负责"产生带时刻的原始读数" |
| 无 `verify` 字段 | 独立 `verify: SignalSpec` | "字节发出"≠"设备生效"，两个断言必须分开 |
| 无 `paused` | `submit(paused=True)` + `go()` | 实验上必须：**由受试者自己启动倒计时**，与"被突然告知"不是同一种测量 |
| 多条 cue 可同时提交 | 后到的默认 `PENDING` + `queued_behind`，前一条刺激结束时自动起拍 | 人只有一双眼睛；两条同时跑的 cue 是第二个把第一个顶掉，而不是两个提示 |
| 状态名即结论 | `status`（状态机）+ `verdict`（结论） | 不要求信号的 cue 到期必为 `timeout`，那是它的成功终态；改名等于改契约 |
| `target_at` 当对外接口 | 对外只收 `target_at_wall`（epoch 秒），`target_at` 留作内部单调时钟 | 进程外算不出我们的单调基准；塞 epoch 会被当成 57 年后，且错过绝对时刻曾报 `verdict: ok` |
| MCP 工具手写 JSON Schema | 签名即 schema（`Annotated` + `Field`），`TOOLS` 只存 `fn` | `add_tool` 只能从签名推导 schema，手写的那份从未被发布 |
| `expect_source=none` = 面板点击算证据 | `none` = 只提醒；`http`/`inject` 才是面板观测 | 一个值两套定义（`PANEL_OBSERVED_SOURCES` 与 `_verdict_for` 相反）；默认 cue 因此变成一个“请按我”的按钮 |
| Two-Rate"缺计划时跟踪旧计划" | `HumanEffector.caps().repeatable = False` | "重放人类上一个动作"= 让人再按一次 RESET，语义完全不同 |
| 无 GIL 约束 | 明确写入架构约束 | 见 §1.3 |

## 六、M1 到此为止的结论

**已验证（机器侧）**：
- 亚毫秒调度：20/40 拍网格落点 0.015~0.285 ms，无累积漂移
- 计数网格正确终止；停滞时**丢弃而非爆发**（`bursts=0`）
- 音频通道非阻塞（稳态 0.36 ms）
- 端到端无偏（合成人类恢复误差 0.00 ms）
- 校准收敛且抗异常值（residual 0.00 ms，异常值位移 0.0 ms）
- 跨进程 IPC 全通路可用；源不可用时优雅降级
- 10/10 自检通过，其中 3 条是为已发现的 bug 专门写的回归测试

**未验证（需要真人）**：
- `human_offset_ms` 的真实分布与符号（NMA 在本机是否成立）
- beep 相对纯视觉的增益幅度
- offset 是否**跨回合成稳定** —— 这是全部价值所系
- `key_latency_s` 的真实值（默认 15 ms 是估计值）

**下一步就是跑它**：在一个**真终端**里执行
```bash
python -m chrono_handoff.cli doctor          # 必须看到 console: yes
python -m chrono_handoff.cli probe --trials 30 --conditions both,visual
```
拿到数据后，`theory.md` §2 与 `README` §6.2 里"±150ms → beep → ±50ms"那组来自 reaction-time 范式的数字就能被替换成本项目自己的实测值。

## 音频通道：跨平台重构（后补）

### 为什么不能"随便接一个播放器"

最初的跨平台想法是逐拍 `subprocess` 调系统播放器（`aplay` / `afplay`）。实测否掉了它：

| 方案 | spawn 中位 | spawn p90 | spawn 最差 | 播放 35 ms 音的进程寿命 |
|---|---|---|---|---|
| `ffplay -nodisp -autoexit` | 9.6 ms | 16.5 ms | **246 ms** | 730 ms |

对比 Windows 现役方案 `PlaySound` 的 **0.25 ms**：劣化约 40 倍，且最差 246 ms
足以摧毁节拍网格。更致命的是它是**非确定性**的——同一段代码偶尔慢 25 倍，
而这正是本项目唯一要测量的东西。

结论：进程外包只能是**最后手段**，且必须被标记为近似精度。

### 采用的分层设计

新建 `audio.py`，后端按精度分级，由 `AudioSink.precision` 上报：

| 后端 | 机制 | 精度 | `play()` 中位 |
|---|---|---|---|
| `sample` | 常驻 PortAudio 流（`sounddevice`），按帧偏移混音 | 采样级 | **0.006 ms** |
| `wav` | Windows `winsound` 异步 | 设备级 | 0.206 ms |
| `cmd` | 外部播放器进程 | 近似 | —— |
| `bell` | ASCII BEL | 未知 | —— |

`sample` 后端是**跨平台的正确答案**，两个显而易见的错误写法都避开了：

- **不是每拍一个流**：开流要几十毫秒。
- **不是 `sd.play()`**：它每次调用走一个新缓冲区，无法相对流时钟定位。

做法是一条常驻 `RawOutputStream` + 一个 `(起始帧, 音色)` 队列。
**块大小只影响提前量，不影响精度**：音可以在块内任意帧偏移起始（`k` 变量），
所以定位精度是一帧，而不是一个块。

### 精度等级是接口的一部分，不是注释

静默降级到 `cmd` 会让一次测量运行带上错误的精度等级，而调用方无从知晓。
因此：

- `default_audio(force=...)` 在强制指定本平台不提供的后端时**抛异常**，不替换。
- `chrono selftest` 的音频项按 `precision` 判断是否可测，而不是按后端名
  （原先硬编码 `sink.name != "wav"` 会误跳过新的可移植后端）。
- `chrono doctor` 打印选中后端与理由；`--audio` 的合法值集中在
  `AUDIO_CHOICES`，避免 CLI/daemon/面板三处漂移。

### 离线可测的混音器

混音逻辑的正确性不依赖音频设备：`_callback` 可以手工驱动。测试因此
覆盖了空闲静音、帧精确落点、**子块偏移**（非块大小整数倍）、
多声部叠加不溢出 int16、**过期起始帧被夹紧而非越界写**、声部回收——
无设备也能跑，且在无声环境里也不会假通过。

### 音调字节必须不变

`tone_pcm16` 与重构前的实现逐字节一致（测试里用旧实现作为 oracle 比对）。
原因很实际：WAV 文件缓存在 `%TEMP%` 并按 `<key>_<freq>_<dur>` 命名，
若字节变了，**已有机器会继续用旧文件、新机器用新音色**，同一实验在
不同机器上听到不同的提示音。

### 顺带发现：两个 UI 套件的假失败

`e2e_resize` 有 4 项、`e2e_theme_drag` 有 3 项长期失败。用 `git stash` 对照确认
**与本重构无关**。根因用 `WindowFromPoint` 与页面级 `pointerdown` 捕获探针定位：

> 合成鼠标事件（`SetCursorPos` + `mouse_event`）只投递给前台窗口。
> 窗口在后台时，**连页面级捕获监听器都不会触发**——事件根本没进渲染进程。
> 而 Windows 会静默忽略来自非前台进程的 `SetForegroundWindow`。

即"拖不动窗口"是**投递失败**，不是产品缺陷。已加共享助手 `scripts/_wininput.py`：
- `focus_window()` 用 `AttachThreadInput` 解开前台锁；
- `synthetic_input_works()` 在断言前**先探测**输入能否送达；
- 送不到时**显式 SKIP 并告警**，而不是把没测的东西报成全通过。

这类"假失败"还有另外三种（尺寸/DPI、一帧滞后、环境残渣），具体形态、判据写法与
校准流程见 [`testing.md`](testing.md)。
